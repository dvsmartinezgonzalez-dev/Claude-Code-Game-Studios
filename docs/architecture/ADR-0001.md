# ADR-0001: Singleton Boot Sequence and Subscribe-Then-Check Pattern

## Status

Accepted

## Date

2026-05-02

## Last Verified

2026-05-16

## Decision Makers

Technical Director, design session

## Summary

BoltSort requires 6 persistent manager singletons (QualityTierSystem, LevelDataSystem, SaveSystem, AudioSystem, GameStateManager, CoinEconomy) that must boot in a deterministic order before any gameplay code runs. This ADR defines how singletons are registered, how their boot order is locked, and how downstream consumers safely subscribe to systems that may already be ready by the time the subscriber initialises.

## Context

### Problem Statement

Unity's scene lifecycle does not guarantee MonoBehaviour `Awake` execution order across objects unless explicitly configured via Script Execution Order. Six manager objects must be guaranteed to exist and initialise in a specific order before any gameplay MonoBehaviour's `Awake` or `Start` runs. Additionally, several managers (LevelDataSystem, SaveSystem) complete async initialisation — subscribers created after those systems are ready would miss the `OnReady` event if they only listen and never check current state.

### Current State

No singleton pattern defined. All manager code is unwritten.

### Constraints

- Unity 6.3 — `FindObjectsOfType` removed; `FindObjectOfType` removed
- `[SerializeField]` on properties/methods is a compile error in Unity 6.3
- `DontDestroyOnLoad` must be called in `Awake` before any scene transition
- `async void Awake()` is unsafe — Unity does not await it; `Start()` on other objects fires before async `Awake()` completes

### Requirements

- Managers must initialise in deterministic order across app launches
- Consumers of async-ready systems must never miss the ready signal
- No scene scan at runtime (`FindObjectOfType` pattern replaced)
- PlayerPrefs writes must flush — `OnApplicationQuit` is not guaranteed on Android OOM kill

## Decision

**All 6 manager MonoBehaviours live in `Assets/Scenes/Managers.unity`**, loaded once at app start. Each calls `DontDestroyOnLoad(gameObject)` in `Awake`.

**Static `Instance` property**, set in `Awake` — never retrieved via scene scan:
```csharp
public static T Instance { get; private set; }

private void Awake()
{
    if (Instance != null && Instance != this) { Destroy(gameObject); return; }
    Instance = this;
    DontDestroyOnLoad(gameObject);
}
```

**Script Execution Order (SEO) — locked boot contract.** Every singleton MUST be registered in Project Settings > Script Execution Order with an explicit negative value:

| SEO | Singleton |
|-----|-----------|
| −100 | `QualityTierSystem` |
| −95  | `LevelDataSystem` |
| −90  | `SaveSystem` |
| −80  | `AudioSystem` |
| −50  | `GameStateManager` |
| −40  | `CoinEconomy` |
| −30  | `LevelProgression` |
| 0    | `SortMechanic`, `AnimationSystem`, `InGameHUD`, `LevelCompleteUI` |

`ProjectSettings/ProjectSettings.asset` must be committed to version control — the SEO lives there.

**Subscribe-then-check pattern** for all async-ready singletons (`OnSaveReady`, `OnLevelDataReady`):
```csharp
// In subscriber's Awake:
system.OnReady += HandleReady;
if (system.IsReady) HandleReady(); // handle already-fired case
```
This eliminates the race condition where a subscriber at SEO 0 misses a ready event fired at SEO −95.

**Scene transitions from SEO 0 only**: `SceneManager.LoadScene` may only be called from gameplay code at SEO 0 or later — never from a manager's `Awake`. A manager's GameObject is destroyed with the outgoing scene before `DontDestroyOnLoad` executes if called during scene unload.

### Architecture

```
App Launch
    │
    ▼
Managers.unity loaded
    │
    ├── Awake SEO −100: QualityTierSystem.Instance ─────────── DontDestroyOnLoad
    ├── Awake SEO −95:  LevelDataSystem.Instance ──────────── DontDestroyOnLoad
    ├── Awake SEO −90:  SaveSystem.Instance ───────────────── DontDestroyOnLoad
    ├── Awake SEO −80:  AudioSystem.Instance ──────────────── DontDestroyOnLoad
    ├── Awake SEO −50:  GameStateManager.Instance ─────────── DontDestroyOnLoad
    ├── Awake SEO −40:  CoinEconomy.Instance ──────────────── DontDestroyOnLoad
    └── Awake SEO −30:  LevelProgression.Instance ─────────── DontDestroyOnLoad
            │
            ▼ (async init completes)
    OnLevelDataReady / OnSaveReady events fire
            │
            ▼ SEO 0 objects subscribe + check IsReady
    SortMechanic, AnimationSystem, InGameHUD, LevelCompleteUI
```

### Key Interfaces

```csharp
// Every DDOL singleton — generic pattern
public class ManagerName : MonoBehaviour
{
    public static ManagerName Instance { get; private set; }

    private void Awake()
    {
        if (Instance != null && Instance != this) { Destroy(gameObject); return; }
        Instance = this;
        DontDestroyOnLoad(gameObject);
        // ... system initialisation
    }
}

// Async-ready singletons expose this pattern:
public bool IsReady { get; private set; }
public event Action OnReady;

// Subscriber (at SEO 0) — subscribe-then-check:
private void Awake()
{
    LevelDataSystem.Instance.OnLevelDataReady += HandleLevelDataReady;
    if (LevelDataSystem.Instance.IsReady) HandleLevelDataReady();
}
```

### Implementation Guidelines

- Set `Instance` and call `DontDestroyOnLoad` in `Awake` — never in `Start`
- Register every new DDOL singleton in Script Execution Order with explicit negative value — omitting this causes silent ordering bugs
- Use `FindObjectsByType<T>(FindObjectsSortMode.None)` — not the removed `FindObjectsOfType<T>()`
- Use `FindFirstObjectByType<T>()` or `FindAnyObjectByType<T>()` — not the removed `FindObjectOfType<T>()`
- Call `PlayerPrefs.Save()` after every `PlayerPrefs.Set*()` — `OnApplicationQuit` is not guaranteed on Android OOM kill
- Never `async void Awake()` — Unity does not await it; `Start()` on other objects fires before the async work completes

## Alternatives Considered

### Alternative 1: ScriptableObject event channels

- **Description**: Replace singletons with ScriptableObject assets that carry events and state
- **Pros**: Decoupled; no scene dependency; designer-friendly
- **Cons**: No lifecycle control; no guaranteed initialisation order; GC allocation on event invoke (forbidden per ADR-0002); no `async`/`await` support for I/O
- **Rejection Reason**: Lifecycle ordering requirements cannot be met; hot-path allocation rule violated

### Alternative 2: Service Locator pattern

- **Description**: Central registry — `ServiceLocator.Get<ILevelDataSystem>()`
- **Pros**: Decoupled from concrete types
- **Cons**: Runtime errors on missing registration; hidden dependencies; harder to test than constructor injection
- **Rejection Reason**: Static `Instance` with SEO is simpler, equally testable, and failure-mode is a compile error rather than a runtime null ref

## Consequences

### Positive

- Boot order is deterministic and auditable (checked into version control via ProjectSettings.asset)
- Subscribe-then-check eliminates ready-event race conditions
- No scene scan at runtime — no per-frame `Find` calls

### Negative

- Every new manager requires a manual SEO entry in Project Settings
- Circular dependencies between singletons become compile errors — must be resolved via events

### Neutral

- Singletons survive scene loads — all 6 managers are always in memory

## Risks

| Risk | Probability | Impact | Mitigation |
|------|------------|--------|-----------|
| New singleton added without SEO entry | Medium | Medium — silent ordering bug, hard to reproduce | Code review checklist item; CI check for SEO registration |
| `DontDestroyOnLoad` called too late (scene transition before Awake) | Low | High — manager destroyed unexpectedly | Keep all managers in Managers.unity; never instantiate managers from gameplay scenes |
