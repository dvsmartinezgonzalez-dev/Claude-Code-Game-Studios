# ADR-0003: Save System Design — Atomic Write and Mobile Platform Safety

## Status

Accepted

## Date

## Last Verified

## Summary

BoltSort's save file must survive app kill mid-write (Android OOM), iOS file protection lockout on cold start, and concurrent background/pause writes without corruption. This ADR defines the atomic write-then-swap strategy, background vs. pause write modes, iOS retry loop, schema versioning, and the `PlayerPrefs` boundary for audio preferences.

## Context

### Problem Statement

Mobile save files face three failure modes not present on desktop:
1. **Mid-write kill** — Android OOM kills the process mid-`FileStream.Write`. A partially-written save file is unrecoverable without a backup strategy.
2. **iOS cold-start file protection** — iOS file protection (class `CompleteUntilFirstUserAuthentication`) makes the save file unreadable for several hundred milliseconds after a cold reboot. A synchronous read in `Awake` at SEO −90 can throw `UnauthorizedAccessException`.
3. **Pause-write deadline** — iOS gives apps 5 seconds after `OnApplicationPause(true)` before suspension. Any `await` in the pause handler returns control to the OS; the write may never complete.

### Current State

No save system exists. This ADR establishes the design before any code is written.

### Constraints

- .NET Standard 2.1 BCL (Unity 6.3) — `File.Move(string, string, bool)` 3-arg overload does NOT exist
- `async void OnApplicationPause()` returns control to OS at first `await` — write never completes under iOS suspension
- `PlayerPrefs` for audio volume: keyed separately from the JSON save file; survives app reinstall differently from file-based saves
- Save file must be human-inspectable for debug builds (JSON, not binary)

### Requirements

- TR-SP-001: Atomic write via `FileStream` + `File.Replace` (write-then-swap)
- TR-SP-002: Save schema fields including `schema_version`
- TR-SP-003: `WriteCompletionAtomic(levelId, bestStars, version, newCurrentLevelId)`: snapshot on main thread + background write
- TR-SP-004: `IsReady` bool + `OnSaveReady` event; subscribe-then-check (ADR-0001)
- TR-SP-005: `PlayerPrefs` for audio preferences; SaveSystem does not mediate PlayerPrefs writes
- TR-SP-006: Integer `schema_version` field; sequential migrators applied on read if version < current
- TR-SP-007: iOS cold-start retry — `UnauthorizedAccessException` catch, 250ms sleep, 5-second timeout
- TR-SP-008: W-1 writes off main thread via `Awaitable.BackgroundThreadAsync`; W-2 (pause) synchronous

## Decision

**Atomic write-then-swap** for all file writes:
```csharp
// Step 1: write to .tmp
using var stream = new FileStream(tmpPath, FileMode.Create);
var bytes = Encoding.UTF8.GetBytes(json);
stream.Write(bytes, 0, bytes.Length);
stream.Flush(flushToDisk: true);

// Step 2: atomic replace
if (File.Exists(savePath))
    File.Replace(tmpPath, savePath, null); // 3-arg, null = no backup
else
    File.Move(tmpPath, savePath);          // first write — no existing file
```
If the process is killed mid-write, the `.tmp` file is corrupt and the existing save survives untouched.

**Two write modes:**
- **W-1 (gameplay write)**: `Awaitable.BackgroundThreadAsync()` + `SemaphoreSlim._writeLock.WaitAsync()`. Snapshot captured on main thread BEFORE `BackgroundThreadAsync()`.
- **W-2 (pause write)**: `OnApplicationPause(true)` — fully synchronous. Uses `_writeLock.Wait()` (not async). Must complete before iOS 5-second suspension.

**`async void OnApplicationPause` is forbidden** — returns control to OS at first `await`. All code in the pause handler must be synchronous. This is the most common save-system bug on iOS.

**iOS cold-start retry**:
```csharp
// In Awake (SEO −90):
DateTime deadline = DateTime.Now.AddSeconds(5);
while (DateTime.Now < deadline)
{
    try { json = File.ReadAllText(savePath); break; }
    catch (UnauthorizedAccessException) { Thread.Sleep(250); }
}
```
Thread must join before `IsReady = true` fires. Not the main thread — spawned from `Awake` via `Thread`.

**Catch both `IOException` and `UnauthorizedAccessException`**: They are sibling .NET types. `catch (IOException)` alone does NOT catch `UnauthorizedAccessException`.

**Schema versioning**: Integer `schema_version` field in the JSON root. Sequential migrators applied on read when `version < currentSchemaVersion`. Migrators must never set `completion_version` on previously-empty records (write-once contract).

**`PlayerPrefs.Save()` after every write**: `OnApplicationQuit` is not guaranteed to fire on Android OOM kill.

### Architecture

```
Main thread (Awake SEO −90)
    │
    ├── try File.ReadAllText(savePath)
    │       └── catch UnauthorizedAccessException → retry 250ms × N (5s max)
    ├── JsonConvert.DeserializeObject<SaveData>(json)
    ├── ApplyMigrations() if schema_version < current
    └── IsReady = true; OnSaveReady?.Invoke()

Gameplay → WriteCompletionAtomic(...)
    │
    ├── [main thread] snapshot = BuildSnapshot()
    └── [background] Awaitable.BackgroundThreadAsync()
            └── _writeLock.WaitAsync()
                    └── WriteAtomicToFile(snapshot)

OnApplicationPause(true)   [main thread, synchronous]
    │
    └── _writeLock.Wait()
            └── WriteAtomicToFile(currentSnapshot)
```

### Key Interfaces

```csharp
public interface ISaveSystem
{
    bool IsReady { get; }
    event Action OnSaveReady;

    // W-1: async gameplay write (background thread)
    Awaitable WriteCompletionAsync(int levelId, int bestStars, int schemaVersion, int newCurrentLevelId);

    // W-2: synchronous pause write (called from OnApplicationPause — no await allowed)
    void WriteBoardSnapshotSync(BoardSnapshot snapshot);

    // Read (called from Awake / foreground restore)
    BoardSnapshot? ReadBoardSnapshot();

    int GetCurrentLevelId();
    int GetCoinBalance();
}

public class BoardSnapshot
{
    public int[][]  StackContents      { get; set; }
    public int[][]  TempSlotContents   { get; set; }
    public int      StackDepth         { get; set; }
    public int      TempSlotDepth      { get; set; }
    public int      TempSlotCount      { get; set; }
    public int      ColorCount         { get; set; }
    public int      MoveCount          { get; set; }
    public long     SequenceId         { get; set; }
    public int      LevelId            { get; set; }
    public string   GsmState           { get; set; } // "Active" | "Complete"
    public bool     WasInBoltSelected  { get; set; } // EC-06 flag
    public bool     IsValid            { get; set; } // set false on deserialization failure
}
```

### Implementation Guidelines

- **Never `File.Move(source, dest, overwrite: true)`** — 3-arg overload does not exist in .NET Standard 2.1; compile error
- **Never `async void OnApplicationPause()`** — use `void`; all SP calls synchronous in pause handler
- Capture snapshot on main thread before `BackgroundThreadAsync()` — background thread must not read Unity APIs
- `SemaphoreSlim` with initial count 1 as write lock — `WaitAsync()` for W-1, `Wait()` for W-2
- `Flush(flushToDisk: true)` on `FileStream` before `File.Replace` — ensures bytes reach disk before swap
- `catch (IOException ex) when (!(ex is UnauthorizedAccessException))` is wrong — catch both independently

## Alternatives Considered

### Alternative 1: Binary serialization (BinaryFormatter)

- **Description**: Serialize `SaveData` to binary using `BinaryFormatter`
- **Pros**: Smaller file size; faster read/write
- **Cons**: Not human-readable for debugging; `BinaryFormatter` is deprecated in .NET 6+; no schema migration path; security concerns (object graph injection)
- **Rejection Reason**: Debugging and migration requirements outweigh size benefits

### Alternative 2: Unity's `PlayerPrefs` for all save data

- **Description**: Store all save fields as individual `PlayerPrefs` keys
- **Pros**: Zero file I/O code; platform-handles atomicity
- **Cons**: `PlayerPrefs` is not atomic on Android (partial flush on OOM kill); no migration support; limited to simple value types; size limit warnings on some platforms
- **Rejection Reason**: Atomicity and migration requirements cannot be met

## Consequences

### Positive

- Write-then-swap means corrupt saves are impossible (old file survives a killed write)
- iOS cold-start retry handles the most common iOS save-load failure mode
- Synchronous pause write guarantees save completes within iOS 5-second deadline

### Negative

- Background write requires careful snapshot capture on main thread before thread hop
- `SemaphoreSlim` adds complexity compared to a simple `File.WriteAllText`

### Neutral

- Schema versioning requires migrators to be written for every breaking schema change

## Validation Criteria

- [ ] OOM kill mid-write: existing save survives; `.tmp` file is orphaned
- [ ] iOS cold-start: `UnauthorizedAccessException` retry loop fires; `IsReady` fires after thread joins
- [ ] Pause write completes synchronously; no `await` in `OnApplicationPause`
- [ ] Schema migration: loading a v1 save in a v2 build applies the v1→v2 migrator
- [ ] `File.Move(3-arg)` and `async void OnApplicationPause` never appear in `src/` (grep check)
